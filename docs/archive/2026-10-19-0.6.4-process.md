# 0.6.4 过程档案——功能性评审落地（2026-10-19）

> 这不是入门路径。公开行为变化看 [CHANGELOG.md](../../CHANGELOG.md) 的 `[0.6.4]` 节。
> 本文只记病灶取证、判据与取舍。归档为冻结记录：其中的套件数量是写下那一刻的实测值。

## 零、起因：一次功能性评审

对全仓做了一轮按域的功能性评审（先文档后代码 + 全量门禁实测复跑：39/39 套件通过，
26.5s→27.5s）。结论分级沿用 AGENTS.md 评审纪律：实测属实 / 部分属实 / 设计取舍 /
无法证实。落地时四条修复、两条明确不改——记录如下。

## 一、出图轮询：同一个物理故障两种判法（P1，部分属实）

**病灶**：`awaitDrawTask` 里传输层抛错（ECONNRESET / DNS）不升级为终局、继续等
下一轮；而同一种 CDN 边缘抖动以 **5xx 响应**出现时直接判 `failed`、作业出表、
进 60s 冷却——agent 想续查只能重新提交。上游排队窗口实测 1–15 分钟
（docs/SPIKE-image-gen.md），那个窗口内的边缘 5xx 是常态噪声。

**佐证**：`draw-runtime.ts` 自己承认「上游偶发返回非 JSON（CDN 错误页）」并为此
做了防御——但那条防御只覆盖 **status=200 的垃圾体**；CDN 错误页通常是 502/503，
走的正是死刑分支。旧测试两条钉子钉死了旧语义（「503 → 上游服务异常」、
「非 2xx 轮询要报错」），所以这是**有出处的 deliberate 行为**，不是漏判。

**修法**：新增纯谓词 `isTransientPollStatus`（408 / 429 / ≥500），轮询响应非 2xx
时先过它——瞬态继续等（deadline 收口成 pending，续查把手不丢），4xx 才走原
终局分诊。`awaitDrawTask` 与 `runDrawOnce` 共用同一循环，一次性形状下的表现是
「预算耗尽 → 超时文案（上游任务可能仍在生成）」，语义不变。

**判据为什么不是「全部重试」**：401/403 = 令牌或权限真没了，404/400 = 任务或端点
真没了——等下去不会变，快速失败 + 冷却是对 agent 的正确信号。

## 二、出图作业表：FIFO 杀能续查的作业（P5，低概率）

**病灶**：`evictIfNeeded` 无脑 FIFO。一个仍在等待线内的 pending 作业被淘汰后，
agent 带 jobId 回来只换来「不在本次会话的作业表里」，而上游任务还在跑——两段式
残缺。

**修法**：两级淘汰。软上限（`maxJobs`）只淘汰**已过续查保护窗**的作业（年龄 ≥
`resumeWindowMs` 的，带回来也只会换来「超过总预算」）；硬上限（`hardMaxJobs`，
默认 2×）保底，全是保护窗内的作业也绝不无界。保护窗由 `index.ts` 传
`settings.drawTimeoutMs`——「表还记不记得」与「工具放不放弃」是同一条线。

## 三、余额缓存键：末 6 位（P3，属实但低危）

**病灶**：`fetchBalance` 的缓存键是 `"balance#" + token.slice(-6)`。两个不同令牌
末 6 位相同的概率在 1/16^7 量级，代价却是一个 TTL（默认 60s）内把 A 的身份的
余额当 B 的返回。缓存键的正确性不该交给运气。

**修法**：FNV-1a 完整哈希指纹。不需要保密、不进日志（与脱敏正则的形状无关）。

## 四、面板：本地计数的依赖不说出口（P2，属实）

**病灶**：四块本地计数的唯一生产者 `usage-observer` 只挂在注册 provider 后的
适配器上，而 provider 默认 opt-in 关——新装用户看到恒为 0/空的计数，形状与
「插件坏了」不可区分。README「三条事实」写着这件事，但界面不说。

**修法**：`quota.countingOff` / `quota.countingPending` 两条提示，由 `LocalDailyCard`
新参 `countingNote` 渲染。**不出提示的第三种情形**：provider 状态读不到（快照省略
+ 兜底 GET 也失败）时 provider 是 `DEGRADED_PROVIDER`——编出来的形状，此时说
「未开启」等于替 Host 断言（与 `balance` 的 `tokenKnownAbsent` 同一条纪律：
判据只能是「读到了令牌状态、且它说没有」）。

## 五、两处明确不改（有出处，不是漏修）

1. **maxTokens 兜底不伪造徽章（P4）**：`cards.ts`  roster 行的输出上限徽章刻意
   「只在有值时画」，并有常驻一行 `provider.maxOutputHint` 解释「没显示 = 走
   32768 兜底」。理由写在 `cards.ts:683` 一带：32768 不是任何模型的属性，是
   harness 的缺省值，画在每一行上会让人以为是平台声明。评审曾建议改成显式
   「32768·兜底」徽章——**不采纳**：把别人的缺省值画成本模型的属性，是用一个
   误导换另一个误导。改文案（把这行提示写得更醒目）可以讨论，改形状不行。
2. **e2e 缺口（P6）**：真 peer 契约（`classifyPiAiError` 措辞命中面、
   `resolveRetryPolicy` 接受面）仍无门禁——那是基建项，留在 docs/ROADMAP.md
   Backlog，不混进本版。
