# 0.5.0 实施过程档案（2026-10-17）

> 本文件是 `CHANGELOG.md` 的 `## [0.5.0]` 一节的**病灶、取证与判据**。
> CHANGELOG 只写「用户看到什么变了」，这里写「为什么这么变、代价是什么、哪条旧裁定被推翻」。
>
> 0.5.0 与 0.4.0 同一天，但两者之间隔了 19 个提交——其中 7 个（趋势改竖向柱状图、
> 出图装配层测试、信任围栏枚举门禁、AGENTS.md、host 侧两条锐评）在 0.4.0 打 tag 之后才落地，
> 所以它们的内容进的是本节。

## 一、窗口徽标的进制：推翻 `formatWindow` 的「一把尺」裁定

**病灶**：`roster` 每行的窗口徽标把 `1000000` 印成 `977K`、`256000` 印成 `250K`、
`200000` 印成 `195K`。用户报的是 `977K` 那一处，实测是同一批产物。

**取证**（`src/host/context-catalog.ts` 的逐条来源注）：

| 策展表/目录里写的 | 上游自己的叫法 | 旧实现印成 |
|---|---|---|
| `1048576` | 1M（档位表也这么写） | `1M` ✅ |
| `1000000` | 1M（智谱官方、MiniMax、models.dev） | `977K` ❌ |
| `256000` | 256K（models.dev 给 LongCat-Flash-Lite） | `250K` ❌ |
| `200000` | 200K（智谱官方 GLM-4.7-Flash） | `195K` ❌ |
| `128000` | 128K（目录声明 / pi-ai 兜底） | `125K` ❌ |

**旧裁定**（原 `formatWindow` 头注，明文）：*「K=1024、M=1024²，与档位值同一把尺。
**不美化**：目录声明的 128000 显示成 125K 而不是 128K——标签必须能从数值反推出来，
四舍五入到好看的整数是撒谎。」*

**判据**：这条原则对 **2 的幂**是对的（`131072 → 128K` 而不是 `131K`，已保留），
错在把它当成**唯一**的尺去量十进制声明。上游自己混用两种写法（档位/出厂规格是 2 的幂，
目录与 models.dev 报十进制），一律除 1024 得到的是**没有任何人这么写的标签**——
LongCat-Flash-Lite 在模型页写着 256K，面板印 250K，用户只能认为面板算错了。
这是与「不美化」方向相反的一种撒谎。

**改法**：按这个数写出来时用的那个进制渲染（≥1M 走 M；能整除 1000 走十进制；
能整除 1024 走二进制；其余按十进制取整，进位到四位数交给 M 档，`999999 → 1M` 而不是
`1000K`）。与姊妹插件 Agnes 的 `tokenSize` 是**同一条规则**，她那份头注记着同一个坑
（*"a flat /1000 rounding once printed 1049k for the 1M window"*）。

**代价（写在函数头注里，并用断言钉住）**：`128000` 两个进制都整除，走十进制 →
与 `131072` 同读 `128K`（相差 2.4%）。对**窗口徽章**值得：它回答的是「大概能放多少上下文」，
而 128K / 256K / 1M 是上游与市场共用的叫法。

**门禁**：`test/catalog.test.mjs` 新增一节——20 条用例取自真实数据（策展表/目录里的值），
外加一条「128000 与 131072 同读 128K」的撞车断言，免得日后被当成 bug「修」回去。

## 二、「推荐」是厂商级事实，不该逐行挂

**病灶**：`FEATURED_OWNERS = ["deepseek-ai", "ZhipuAI", "Qwen"]` 列的是 **owner**，
字典里也写着「推荐**系列**（深度求索 / 智谱 / 通义千问）」，但渲染是逐行判断的
（`FEATURED_OWNERS.includes(catalogOwner(row.id))`）→ 同名厂商的十几行各挂一枚。

**为什么现在才显形**：清单平铺时，逐行徽标是唯一能标「它属于推荐厂商」的方式；
按 owner 分组之后，组头（厂商名）+ 置顶位置 + 每行徽标在说同一件事。

**改法**：每组一枚、挂组头。留着而不是删掉，是因为它同时**解释置顶原因**——
只靠位置置顶，读者看不出凭什么是这三家在上面。

**门禁升格**：原来只断言 `bodyText` 里**有**「推荐」（逐行重复到 6 枚照样绿），
改成计数——fixture 三个 owner 全在置顶集 → **恰好 3 枚**。

## 三、行名的 `owner/` 前缀：「行宽还给名字」当初没做到

**病灶**：分组那笔提交声称「消掉 12 个重复前缀，行宽还给名字」，而市场截图里每一行
仍是 `deepseek-ai/DeepSeek-V4-Pro-0813`。原因在 Host 侧：魔搭目录**只回 id**，
`llm-models.ts` 的 `str(entry.name, id)` 兜底让 `name === id`，所以行名与组头逐字重复。

**改法**：`trimOwnerPrefix(id, name)`（`const.ts`）——只切**与 owner 逐字相同**的前缀；
name 若是目录给的人话名字或来自别的 owner，原样返回（不按位置硬切）。完整 id 留在
行的 `title` 与复选框的 `aria-label` 上，切掉的信息没有丢。

**教训**：宣称与实测要分开核。这处是**看着截图**发现的，测试全绿——因为渲染套件的
fixture 喂的是人话名字（`DeepSeek V3`），碰不到真实形态。

## 四、本地计数是「本客户端」的口径（三处过度宣称）

**病灶**（用户实测发现）：桌面端的本地调用次数在 Web 端看不到。

**取证**：这是**裁定**，不是缺陷——`usage-store.ts` 头注写着：状态落在
`$DSH_HOME/state/[<profile>/]<name>/usage.json`，*「按 profile 分段（它回答的是
「这个 profile 的调用吃了多少额度」……没有共享跨 profile 的理由）」*；
`doctor.ts` 按 profile 逐个读作用域并并排列出。

**问题在措辞**：面板图例、README「诚实声明」、AGENTS.md 三条事实三处都写成
「注册 provider 后 DSH 的全部魔搭调用都经本插件，所以**覆盖全部 DSH 魔搭调用**」——
在一台机器上同时用桌面端与 Web 端时**不成立**。

**改法**：三处改成「只统计**本客户端**经本插件的调用（桌面端与 Web 端各记各的）」，
并点明 `npm run doctor` 会列出各 profile——那是「另一个客户端的数字去哪了」的答案。
区块标题同步：`本地调用（仅经本插件的调用）` → `本地调用（本客户端 · 仅经本插件）`。

**为什么不合并成一份跨 profile 的账**：两个 profile 是两个 Host，各自持有自己的状态目录；
让其中一方去读另一方的账，等于给「谁拥有这份数据」引入第二个主人，且要处理另一方正在写。
真需要合并视图时，正确的落点是 doctor（只读、离线、看得见全部 profile），不是面板。

## 五、裸后缀 `t`

用户问「`2 · 21,695t` 说起来这个是啥意思」——`t` 既不是 K/M 那样的量级后缀，
也不是任何语言的单位词。改为两个读数各走字典（`{calls} 次` / `{tokens} token`），
单位跟着语言走。

**没改成 K/M**：Agnes 的 `tokenSize` 会把 `21695` 抹成 `22K`，而本面板的卖点正是
「精确的本地计数」；量级后缀解决的是宽度问题，这里要解决的是歧义问题。

**顺带保住的一条**：`tokens` 为 `null`（上游没给用量）时整段不画，仍然不画 `0 token`
——「读不到 ≠ 0」（`usage-observer` / `usage-store` 的既有语义）。

## 六、趋势「显示天数」与「保留窗口」解耦

**病灶**：趋势图能画多少天，取决于 `trendDays`；而天桶修剪用的是同一个数——
把显示窗口调大并不能看到更远的日子，因为更早的桶已经被剪掉了，画出来是 0，
与「那天真的没调用」不可区分。

**改法**：`trendDays`（显示，默认 14）与 `retentionDays`（保留，默认 90）分开，
显示窗口恒被夹在 `[1, retentionDays]`。

**选择存哪**（三选一的取舍）：

- 不存 `usage.json`：它是**观测热写路径**（每次真实调用都写），版本漂移会让新键被旧构建
  丢掉或反过来；显示偏好不该绑在一条每秒都可能被写的文件上。
- 不存 `provider.json`：语义不对（那是「接入」的设置）。
- **新开 `usage-prefs.json`**（按 profile 分段）：它的写频率是「用户点选择器」，
  与 `provider.json` 同级。

**一条不能省的话**：显示窗口调大**不能**恢复已经剪掉的历史——那些日子会渲染成 0。
保留窗口只在「当时就留了」的前提下有意义。

## 七、接入卡顶部去重与「上下文窗口覆盖」

**病灶一（三行说同一件事）**：区块标题「接入为 DSH 模型」+ 开关标签「已接入」+
状态行「已注册」——读起来像三件不同的事。改法：并成一行
`已接入 · 已注册（模型可在选择器里选用） · 面板`。两个词都留着：开关是**面板里的
开关状态**，注册是**Host 里的落地情况**，两者可以不一致（开着但还没注册完）。
失败仍单独一行走 `role=alert`，且此时不再重复一句话状态——error 与 registered 可以
同时为真（回滚到旧对的状态），两句挂一起会互相打架。

**病灶二（措辞名不副实）**：档位选择器叫「上下文窗口」、默认档叫「默认（跟随目录）」，
而它恰恰是**盖过目录与策展表**的那一级（真值链：目录声明 > 用户覆盖 > 策展表 >
128K 兜底）——它不「跟随」任何东西。改法：标签「上下文窗口覆盖」、默认档
「不覆盖（默认）」、提示明说「会盖过内置策展表」；位置从开关旁边沉到卡片最底，
不再冒充主流程。

**一条保留**：清单行徽章的 tooltip 继续用泛称的「上下文窗口」，所以新开了
`provider.contextWindowOverride` 键，没有改写旧键的含义。
