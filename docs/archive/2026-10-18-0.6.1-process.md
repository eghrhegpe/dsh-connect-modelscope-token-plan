# 0.6.1 过程档案——迁移窗口期的状态可见性（2026-10-18）

> 这不是入门路径。公开行为变化看 [CHANGELOG.md](../../CHANGELOG.md) 的
> `[0.6.1]` 节。本文只记病灶、判据与取舍——全部来自第二轮功能性评审
> （2026-10-18，报告见用户侧评审文档，结论分级：R1 实测属实 / R2 实测属实 /
> R3 部分属实 / R4 实测属实）。

## 一、病灶一：`inheritFrom` 是死参数，且形状有害（R1）

`state-store.ts` 的 `createStateReadCache` 带一个 `inheritFrom` 选项（profile
分段前共享布局的一次性迁移缝），**四个 store 无一带它**——实际继承是
provider-store 在读穿透闭包里手写的（`:311-336`）。三问题叠加：

1. 死代码 + 文档误导：state-store 头注与 provider-store 注释都把继承描述成
   「走这个缝」，读者会以为它是共享基础设施；
2. 有害形状：它的写回是**读路径内直接触发的写**，不经 store 的写队列——
   正是 provider-store 注释里「咬过三次」的竞态形状（继承写与并发用户保存
   竞争，继承只发生一次，被盖掉的保存永久丢失）；
3. 测试只覆盖退化路径（legacy 也读不到），写回成功路径零覆盖。

**修法（删除而不是接线）**：删参数、删头注对应段落，把「读路径内触发的写
必须过本 store 写队列」作为裁定写进 `createStateReadCache` 的说明；provider
/ usage-prefs 的手写缝保持原样并在各自头注留指针。想复用的正确形状是给缓存
原语注入 writeQueue 再删手写版——那要动三个 store 的热路径，0.6.1 不做。

## 二、病灶二：doctor 在迁移窗口期藏旧数据（R2）

`doctor.ts` 的共享作用域报告与 `profiles.length === 0` 耦合：机器上**有过任何
profile 作用域**时，共享布局整份从报告、渲染、症状里消失。复现（两台目录并存、
均版本已知可解析）：`profiled: true / scopes: [desktop days=1] / shared: null /
symptoms: (none)`——而 `state/<name>/usage.json` 带着 42 次历史调用好生在盘上。
迁移窗口是真实存在的：① 旧版在无 `profileContext` 的宿主上跑过（profile=null
→ 写共享目录，这是 state-store 明文的降级路径）；② provider.json 的继承回填
只搬 provider.json 一个文件，其余三个文件的旧共享副本永久留在盘上。

**修法**：共享目录**在场就报**，label 打 `shared (legacy)`，与 profile 作用域
并排列出；症状与渲染同步。测试新增 §5b（并存 → 两者都报 + 共享里的损坏文件
进症状表）。**未改**「零 profile 时报 shared」的既有语义（§5 原样通过）。

## 三、病灶三：四个 store 的继承不一致，三缺一无出处（R3）

| 文件 | 旧共享布局继承 | 出处 |
|---|---|---|
| provider.json | 有（一次性、过写队列） | provider-store `:254-258,311-336` |
| usage-prefs.json | **本版补上**（同款手写缝） | 头注 + §9 回归 |
| draw.json | 无 | 有裁定，但前提不完整（见下） |
| usage.json | 无 | **本版补记裁定** |

- draw 的裁定原文「draw.json 晚于按 profile 分段诞生，市面上不存在共享旧
  draw.json」只对**宿主一直提供 profileContext** 的机器成立；宿主不提供的
  机器上 profile 恒为 null，draw.json 至今仍写共享目录，宿主升级后同一个
  迁移窗口一模一样。已修正前提并补一句「那种窗口里不继承不搬，doctor 报
  shared (legacy)，开关与偏好回 patch 默认」。
- usage.json 补记「不搬」裁定：无 profile 时期的账不属于任何一个 profile，
  整段搬过来是把那段时间算成这个 profile 的；doctor 报出来让操作者自己看
  （诊断可见 > 静默搬运）。
- usage-prefs 是单值显示偏好，回填无害，本版**补齐继承**（与 provider 同款：
  读路径内触发、回填过本 store 写队列、显式清除不复活、foreign 版本不覆盖）。

## 四、病灶四：临时文件清理只覆盖 rename 失败一条路（R4）

`writeStateFile` 的 `writeFile`（磁盘满）/ `open` / `handle.sync()`（EIO）
三条失败路径都直接抛出，半截临时文件留在 state 目录——正是 rename 注释里
「慢慢堆满垃圾、没有任何代码会去清」的同一个坑。**修法**：try 覆盖到 rename
成功为止，catch 里 unlink 再重抛（unlink 失败 `catch {}` 不掩原始错误）。

测试注入点：临时路径预置**只读文件**，`open(tmp, "r+")` 在 Windows 抛 EPERM、
POSIX 抛 EACCES（本机实测两种平台行为）；根用户跳过（root 绕过权限位，
注入点不成立，不跳会假绿/假红）。

## 六、踩坑记录

- **首轮全量跑出 1/39 失败**：把 `npm run build` 排在测试之后的同一条命令链
  里，build-gate 按设计抓到「改了 src 未重建」——门禁是对的，命令链顺序是
  错的。改回「先 build/先跑门禁」后 5 连绿。
- **Edit 工具对含 CJK 的旧串反复 mismatch**（「读过但没有」被看丢一字、
  节线 `─`(U+2500) 被当成 `—`(U+2014)）：含中文的替换一律先用 Python
  repr 核对磁盘原文再改。
- **Git Bash 的 `/tmp` 与 Windows Python 不通用**：bash 的 `cp`/heredoc 写的
  `/tmp/x`，Python `open('/tmp/x')` 找不到——跨 shell 传递临时文件用仓库内
  相对路径。

## 七、第三轮评审的两条修复（R6 注释 / R7 读数，同日追加）

0.6.1 主体提交后做了第三轮评审（对象：并行会话的 maxTokensOverrides 与趋势图
两个新提交 + 首二轮未细读模块），两条实测问题当天修掉：

- **R6（部分属实）**：maxTokensOverrides 的三处注释宣称「每次 publish 现读、
  改覆盖下一轮轮询就生效、不用重启」。实测 `resolveSettings` 生产侧只有
  `index.ts:50` 一个调用点（apply 时一次性解析），publisher 构造期捕获引用
  （`provider-publish.ts` 的 `effectiveSettings`）——没有按轮询重新解析的路径，
  真实触发是 reload（apply 重跑）。父版本 apiBase 并无此注释，措辞是从
  llm-adapter 里凭据域「每次请求现读」（真现读）借来的。修法：三处注释改成
  实话（构造期读入、patch 改动需 reload），不动行为；要做到「下一轮生效」得把
  `deps.settings` 改 getter 或在 publish 前重新 resolve，那是行为变更，没混进来。
- **R7（cosmetic）**：`compactCount(999_999)` 渲染成 `"1000k"`——按原始量级
  分档、档内 toFixed(0) 进位溢出，且旧测试把这个伪影当边界钉过。修法：分档
  按进位后量级判（`tiers.entries()` 迭代，trim 结果 ≥1000 即进上一档），
  `999_999`/`999_999_999`/`999_499` 与负数进位点补进 panel.test.mjs §5d。
  变异检验 1/1 KILLED（`if (i === tiers.length - 1 || Number(shown) < 1000)`
  → `if (true)`：断言 `compactCount(999999) 应为 1m` 红）。
- 新踩坑：**run-all 39/39 全绿 ≠ typecheck 干净**。tsdown（build）不做类型
  检查，`noUncheckedIndexedAccess` 下 `tiers[i]` 解构的 TS2488 在全量测试里
  无声通过，只有 `npm run typecheck` 抓到。先 build 再全量之后，typecheck
  也要单独跑一遍——三个门禁互相不覆盖。

## 八、第四轮评审的 R8 修复：收敛链防毒化（同日追加）

对象是前三轮未深读的高风险面（inference-client / provider-reconcile /
publish-core / use-snapshot-polling）。R8 实测属实（离线复现）：收敛器的串行
链 `chain = chain.then(executor)` 不吸收 rejection——executor 任何一次未预料
的反抗都把 `chain` 变成永久 rejected，之后每次 `reconcile()` 的 cb 永不执行
（实测：同步抛一次 →「故障恢复」后再触发，publish 恒 0；路由永远回放那次
古老的错误；轮询侧 `void reconcile()` 每 tick 一次 unhandled rejection）。

**定级要诚实**：生产侧三个 store 方法全是 `async`（同步抛不可达），其余
runOnce 路径也都有 try/catch——所以这是**当前不可达的脆弱面 + 全仓唯一漏
防毒化的链**，不是活疮。判它为缺陷的依据是范式不一致：`publish-core.ts` 的
`createPublishQueue` 与 `state-store.ts` 的 `createStateWriteQueue` 都做了
`chain = run.then(() => undefined, () => undefined)`，本文件自己的链曾漏。

修法（两层，各有一条回归 + 一个变异杀死）：

- **链防毒化**：`const result = chain.then(executor); chain = result.then(
  () => undefined, () => undefined); return result;`——本触发的拒绝照常呈报
  给调用方（路由 respondError 看得见），链永不中毒。测试 §9② 钉「executor
  意外反抗如实 reject + 恢复后链还活着」。
- **readDesired 同步抛降级**：`settle()` 把同步抛与异步拒收都收成 null
  （同步抛曾在 `Promise.all([a(), b(), c()])` 的数组构造处逃逸）。测试 §9①
  钉「store 同步抛 → 按未设置降级、收敛照常、恢复后继续 publish」。
- 轮询/挂载两处 `void reconcile()` 补 `.catch` + warn：链防毒化后 executor
  级反抗只可能是未预料 bug，该留档，且不许以 unhandled rejection 到达进程级。
- 变异检验 2/2 KILLED（`chain = result` 退回 → §9② 红；settle 退回
  `.catch(() => null)` → §9① 红）。全量 39/39、typecheck 干净、产物已重建。
- **不进 CHANGELOG**：当前不可达（用户观察不到），按本文件开头的判断标准
  只进 commit message 与本档案。

## 九、R6 的后续裁定：不做 per-poll 活生效（2026-10-18）

R6 修注释时留过一个口子：「要做到下一轮生效，得把 `deps.settings` 改成 getter
或在 publish 前重新 `resolveSettings`」。这里把它焊上——**不做**，理由是
结构性的，不是懒：

- `settings` 是**全 wiring 共享的一份快照**：publisher（构造期捕获）、
  reconciler、四条 provider 路由、snapshot 聚合都从 `index.ts` 的同一份读。
  只让 `maxTokensOverrides` / `apiBase` 两个字段活，会造出「同一份配置里
  两个字段两种生效时机」的两种真值链——比现在的快照语义更难推理，不是更好。
- 要**全量**活生效，需要的不是「publish 前重新 resolve」，而是一次 wiring
  重活化：重注册路由（`allowedHosts` 换了围栏就换了）、重建轮询定时器
  （`pollSeconds` 换了 cadence 就变了）、重读各 store 的 profile 上下文……
  那是插件生命周期的设计，属 ROADMAP 级事项，不是注释能兑现的便宜事。
- 现状即正确边界：注释已写真话（构造期读入、reload 才生效），与「patch 是
  部署层默认、操作者带着 reload 编辑」的既有语义一致。谁再想「修」这个，
  先读完本节再动手。
